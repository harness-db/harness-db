# Positioning: what HARNESS-Review adds over existing harness surveys

Status: delta memo v1, written 2026-09-16 after reading every competitor in full (arXiv HTML for three, PDFs for the two survey papers, plus both public catalogs and both Hugging Face dataset cards). Replaces the stub.

Correction to the execution plan before anything else. The plan's "fourth competitor" is actually two different papers that share a topic and an acronym-style formalism but not authors, venues, taxonomies, or datasets:

- **Li et al., "Agent Harness Engineering: A Survey"** (first author Junjie Li; co-first Xi Xiao, Yunbei Zhang, Chen Liu; corresponding Tianyang Wang, Chandan K. Reddy; CMU/UAB/Tulane/Yale/Amazon). OpenReview `eONq7FdiHa` (TMLR submission), PDF at `picrew.github.io/LLM-Harness/main.pdf`. Proposes **ETCLOVG**. Catalog: `github.com/Picrew/awesome-agent-harness`. "Picrew" is the GitHub org, not an author; cite as Li et al. 2026.
- **Meng et al., "Agent Harness for Large Language Model Agents: A Survey"** (Qianyu Meng, Yanan Wang, Liyi Chen et al.; Xiaohongshu). Preprints.org DOI `10.20944/preprints202604.0428` (v3; a v4 PDF is on HF). Proposes **H = (E, T, C, S, L, V)** and the **Harness Completeness Matrix** (23 systems). Catalog: `github.com/Gloriaameng/Awesome-Agent-Harness`.

Both Guo (Table I, refs [55] and [56]) and Banu (§2.5) treat them as separate works, and Li §2.3 explicitly positions ETCLOVG against Meng's tuple. So there are five prior taxonomies to reconcile, not four. Everything below covers all five.

## A. One paragraph per competitor

### A1. Guo et al., arXiv:2606.20683 (v1, 14 Jun 2026), "From Question Answering to Task Completion: A Survey on Agent System and Harness Design"

**Definition (§2.4, verbatim):** "Following [22, 7, 64], we use harness to denote the runtime infrastructure that surrounds the model and realizes closed-loop agent execution. The harness is broader than an individual tool, memory module, prompt template, or workflow script. It is the coordinating layer that decides which observations reach the model, how context is assembled, how the agent loop advances, how actions are executed, how state and artifacts persist, and how failures are detected, governed, and recovered." Formalized as Eq. (2) H = ⟨I_obs, C, L, I_act, S, V⟩ and Eq. (1) A_LLM = ⟨M, H⟩ (§2.2), where M may be a set of models. **Taxonomy:** deliberately not a component taxonomy ("Our goal is not to introduce another component taxonomy", §1.2). The organizing lens is four engineering paradigms (prompt engineering, workflows/context engineering, harness engineering, agent-native training and co-evolution; §4), six runtime responsibilities (observation interface, context manager, control loop, action interface, state and artifact store, verification and governance; §5.1–5.6), a harness-aware task taxonomy (horizon L1–L4, environment type, autonomy; §6.1) and a task-property-to-configuration mapping (Table V). **Coverage:** ~262 references spanning 2020–2026 (§1.4); no system count; Table X profiles 13 harness families; Table VII compiles ~35 model-harness rows on SWE-bench Verified; Table VIII/Fig. 6–7 use the Terminal-Bench 2.0 public submission repository (75 submissions, 32,604 trial records, 48 strictly matched to the leaderboard; §7.4); Table IX compiles WebArena results by backbone. **Method:** narrative; sources "prioritize high-impact and verifiable sources" (§1.4); no search protocol, inclusion criteria, screening, or agreement statistics. **Dataset:** none coded; an awesome-list (`github.com/ggjy/Awesome-Agent-Engineering`). **Design vs outcomes:** yes, but at the level of harness *identity*, not design features. §7.3–7.5 report within-model spreads across named harnesses (e.g., GPT-4o 23.2% SWE-agent vs 38.8% Agentless; among 20 Terminal-Bench models with ≥3 harness results, median within-model range 13.6 points, 14/20 vary ≥10 points; GPT-4o on WebArena 13.1% model-only vs 54.6% WebOperator). No design dimension is coded, so nothing is regressed on design.

### A2. Rombaut, arXiv:2604.03515 (v2, 10 Apr 2026), "Inside the Scaffold: A Source-Code Taxonomy of Coding Agent Architectures"

**Definition:** the paper never uses "harness"; it uses "scaffold". Abstract (verbatim): "the scaffolding code that surrounds the language model (the control loop, tool definitions, state management, and context strategy)". No numbered definition. Prompt engineering strategy is explicitly excluded from the taxonomy (§6.1), and developer configuration files such as CLAUDE.md are treated as "developer-facing configuration" rather than scaffold architecture (§2.3). **Taxonomy:** 12 dimensions in 3 layers, grown from 9 analysis dimensions by open coding (§3.2). Layer 1 Control architecture: Control loop strategies (§4.1.1, Table 2), Loop driver (§4.1.2, Table 3), Control flow implementation (§4.1.3, Table 4). Layer 2 Tool and environment interface: Tool set design (§4.2.1, Table 5), Edit and patch format (§4.2.2, Table 6), Tool discovery strategy (§4.2.3, Table 7), Context retrieval paradigm (§4.2.4, Table 8), Execution isolation (§4.2.5, Table 9). Layer 3 Resource management: State management (§4.3.1, Table 10), Context compaction (§4.3.2, Table 11), Multi-model routing (§4.3.3, Table 12), Persistent memory (§4.3.4, Table 13). Five cross-cutting themes (§4.4): sampling vs iteration, sub-agent delegation, online vs offline selection, ecosystem maturity, IDE as architecture. **Coverage:** 13 open-source coding scaffolds selected from a pool of 22 (Appendix A gives exclusion rationale), each at a pinned commit (Appendix B). Explicitly "not exhaustive" (§3.1). **Method:** qualitative case study with a three-level template (observation / classification / evidence with file path and line number, §3.4); single author with LLM-assisted code navigation; a post-hoc verification pass checked 296 claims (267 confirmed, 19 corrected, 10 accepted as simplifications; §6.1). No second coder, no kappa. **Dataset:** in-paper tables; per-agent "analysis documents" are referred to (§3.4, §6.4) but no repository URL is given. **Design vs outcomes:** none by design: "No performance benchmarking was conducted, and no claims are made about correlations between scaffold design and task success rates" (§3.5); §5.5 argues benchmark scores confound scaffold, model, and configuration.

### A3. Banu, arXiv:2605.12239 (v1, 12 May 2026, cs.PL), "Harness Engineering as Categorical Architecture"

**Definition (abstract, verbatim):** "The agent harness—the system layer comprising prompts, tools, memory, and orchestration logic that surrounds the model". §3.4: "The harness is not one component of the Architecture—it is the Architecture", i.e. the ArchAgents triple (G, Know, Φ): G = syntactic wiring graph of modules and typed ports, Know = structural certificates (τ, σ, evds) (Definition 1), Φ = deployment map Stages → Models (Definition 2). **Taxonomy:** none; a correspondence between the four "externalization pillars" of Zhou et al. (arXiv:2604.08224) and the triple: Memory ↔ coalgebraic state (§3.1), Skills ↔ operad-composed objects with serial/parallel/trace composition (§3.2, §5), Protocols ↔ wiring G with integrity labels on ports (§3.3), Harness ↔ full architecture (§3.4). §2.5 relates to Meng's tuple: "E and T contribute wiring and realizations, C and S expose state, and L and V are the natural surfaces on which Know-level certificates can be defined and replayed", and says "A precise mapping between the two formalizations is developed elsewhere." **Coverage:** one reference implementation (Operon, `github.com/coredipper/operon`), five compiler targets (Swarms, DeerFlow, Ralph, Scion, LangGraph), one two-model one-task escalation experiment (§6.2), and a 10-instance SWE-bench-lite run with two 8B models where 0 instances resolved (§6.4, §6.4.1). **Method:** formal correspondence plus small experiments; not a survey. **Dataset:** none (code only). **Design vs outcomes:** the SWE-bench-lite comparison of baseline vs three-stage organism vs LangGraph-compiled organism is a design-vs-outcome test, but with N = 10 tasks and 0 resolutions the author concedes it "is still under-powered to discriminate" (§6.4). Its usable claims are model-parametricity of harness structure (Φ) and certificate preservation under compilation (Table in §4.3, §6.3).

### A4. Li et al., OpenReview eONq7FdiHa (under review, TMLR), "Agent Harness Engineering: A Survey" (ETCLOVG)

**Definition (§1, verbatim):** "An agent must receive relevant context, invoke tools through stable interfaces, preserve state, recover from failures, expose its actions for inspection, verify outcomes, and operate within defined permissions. We refer to the surrounding operational infrastructure that provides these functions as the agent harness." Scope (§2.4, verbatim): "the harness is the engineered wrapper that turns model calls into bounded, stateful, tool-mediated task execution through execution substrates, tool interfaces, context control, orchestration, observability, evaluation feedback, and governance constraints"; out of scope unless adapted to agents: "a thin model API wrapper, prompt library, static dataset, generic container runtime, vector database, APM dashboard, or content filter". §2.2 treats prompt engineering and context engineering as narrower scopes that harness engineering "integrates". **Taxonomy:** seven layers, ETCLOVG (§2.3): Execution environment and sandbox (§3), Tool interface and protocol (§4), Context and memory management (§5, organized by time horizon: short/mid/long-term), Lifecycle and orchestration (§6; state management is deliberately folded in here), Observability and operations (§7), Verification and evaluation (§8, a five-stage task-to-feedback lifecycle), Governance and security (§9; lifecycle hooks and policy enforcement live here). Three cross-layer effects (§11): cost–quality–speed trilemma, capability–control tradeoff, harness coupling problem. **Coverage:** "more than 170 open-source projects" (abstract); catalog snapshot frozen 2026-05-08 with 171 entries, 146 GitHub (Appendix A); Table S1 assigns one primary layer to 138 technical artifacts (E 20, T 12, C 9, L 47, O 15, V 21, G 14); Table 2 codes 18 orchestration systems by primary pattern and execution model; Table 4 codes 10 systems on 6 governance features; Table S2 gives layer coverage for 6 reference implementations. The live catalog has since grown to 368 entries (README, last verified 2026-09-14). **Method:** §2.5 "systematic mapping ... using the reporting discipline of systematic reviews to make the source streams, search strategy, and selection process explicit (Page et al., 2021)"; four source streams; inclusion criteria (§2.6); coding protocol (§2.7): multi-label, one primary layer, "single-primary-coder protocol with author audit rather than a formal multi-coder agreement study, so we do not report Cohen's kappa"; corpus limitations (§2.8). No search hit counts, no flow diagram, no screening record, no pre-registration. **Dataset:** the HF dataset `ChenLiu1996/Agent-Harness-Engineering` contains only the PDF. The GitHub catalog ships `data/projects.yaml` (368 entries) with fields `name, repo_url, category (one of 9 catalog categories), summary_en/zh, tags, stars_snapshot, updated_at, license, why_included`. That is a one-category coding plus free-text tags and a one-sentence inclusion rationale per project; it is not a per-dimension coding and carries no per-cell evidence pointers. **Design vs outcomes:** none of their own; §1 cites Bölük (edit-tool change, up to 10× for one model across 15 models), Trivedy (DeepAgents 52.8% → 66.5% on Terminal-Bench 2.0) and Meta-Harness; §12.5 calls for factorial model-by-harness evaluation.

### A5. Meng et al., Preprints.org 202604.0428 (v3/v4, Apr 2026), "Agent Harness for Large Language Model Agents: A Survey" (H = (E,T,C,S,L,V))

**Definition (Definition 2.1, §3.2, verbatim):** "An agent harness is a software system H = (E,T,C,S,L,V) that implements six runtime governance functions: E—Execution loop: Manages the observe-think-act cycle, including turn sequencing, termination conditions, and error recovery; T—Tool registry: Maintains a typed, validated catalog of available tool interfaces; routes and monitors tool invocations; C—Context manager: Governs what information enters the model's context window across turns, including compaction, retrieval, and prioritization strategies; S—State store: Persists task-relevant state across turns and, optionally, across sessions; provides recovery from partial failures; L—Lifecycle hooks: Pre- and post-invocation interception points for authentication, logging, policy enforcement, and instrumentation; V—Evaluation interface: Instruments the execution to capture action trajectories, intermediate states, and success signals for offline analysis, through standardized hooks that distinguish the V-component from general logging". Necessary conditions: E and T; sufficient: all six "with production-grade reliability" (§3.2). ReAct is "not a harness" (framework primitive); LangGraph is called "not a harness" in §3.2 but a "topology-encoded harness" in §3.2/§3.3; MemGPT is a capability module; AIOS a full harness. **Taxonomy:** six categories by stack position (§5.2): Full-Stack Harnesses (Claude Code, OpenClaw/PRISM, AIOS, OpenHands), Multi-Agent Harnesses (6), General Frameworks (3), Specialized Harnesses, Capability Modules (5), Evaluation Infrastructure (4); nine cross-cutting challenges (§6: sandboxing/security, evaluation, protocol standardization, runtime context management, tool use/registry, memory architecture, planning/reasoning, multi-agent coordination, compute economics); 14 research directions (Table 19). **Coverage:** "over hundred papers" (abstract; README says 110+, HF badge says 150+); 23 systems in Table 4 (the text says 22 in three places and 23 in others). **Method (§5.1.1, verbatim):** "We adopt a structured expert survey approach rather than a PRISMA-compliant systematic review". Inclusion: publicly documented, ≥3 of the six components, accessible. Search: keyword search of ACL/NeurIPS/ICLR/ICML/AAAI Jan 2023–Mar 2026, snowballing, GitHub ≥500 stars, practitioner reports. Coding (§5.1.2): three-source verification with documentation authoritative; ambiguous cells "annotated [D] (disputed) in the extended data" (no such extended data is published); closed-source ratings to be read "as 'at least partial'". §3.3.1 concedes the six-tuple is "a theoretically proposed framework, not an inductively derived taxonomy" and lists its own validation as future work. No kappa. **Dataset:** the HF dataset `GloriaaaM/LLM-Agent-Harness-Survey` contains only the PDF and README; the completeness matrix exists only as an HTML table in the README (23 × 6 ✓/≈/✗ plus Security and Multi-agent columns). No CSV, no evidence per cell. **Design vs outcomes:** none of their own; the paper aggregates third-party anecdotes (Grok Code Fast 6.7% → 68.3% via edit-tool format, Fig. 4; DeepAgents +26%; Meta-Harness 76.4 vs 74.7; SkillsBench +16.2 pp with 16/86 tasks negative; AgencyBench native-ecosystem effect; Vercel 15 → 2 tools raising accuracy 80% → 100%, §6.4.4).

**Points of disagreement that matter for our coding manual:**

1. *Prompt.* Four of five include it; Rombaut excludes it. Our A1 keeps it, but the manual must say that a static prompt template alone does not make a harness (Meng §3.1 agrees).
2. *Sandbox.* Everyone includes it but files it under different layers (E, V, Layer 2, challenge, G). Our layer G is closest to Li's E; the crosswalk must map G to Li-E, Guo-V, Rombaut-"Execution isolation", Meng-Security column.
3. *Evaluation.* Meng and Li admit benchmarks and evaluation frameworks as corpus members; Rombaut and we exclude them from the systems table. This is the single largest source of disagreement about what N counts, and it explains why Li's "170+" and our 150–300 are not comparable numbers.
4. *State.* Li merges state into lifecycle; Meng makes it a component; Rombaut makes it two dimensions. Our D layer matches Rombaut and Meng.
5. *Unit.* Li's unit is any harness-relevant artifact (sandbox products, tracing platforms, gateways); Meng's, Guo's, Rombaut's and ours is an agent system. A crosswalk to Li at the system level must therefore restrict to Li's L-layer entries (47 primary) plus the six reference implementations in Table S2.

## D. Gaps, convergence, conflicts

**Dimensions none of the five treats as a coded design variable** (only examples or none):
- F3 `timeouts`: Guo measures timeout *rates* as an outcome; nobody codes the timeout *policy*.
- G2 `filesystem_access`, G3 `network_policy`: everyone subsumes these under isolation or permission; nobody separates them.
- H2 `replayability`: discussed as an aspiration (Li §12.3, Meng §6.11.2), never coded.
- A1 `system_prompt_style`: discussed as a practice (Li §5.3), excluded by Rombaut, coded by nobody.
- M6 `pinned_version`: only Rombaut pins commits; neither survey does.
- A4 `observation_format`: Guo has the concept (§5.1); no one has values or per-system coding.
- B3 `edit_primitive`: Rombaut only (5/13 string replacement). Given that the two most-quoted "harness matters" anecdotes (Bölük; Grok Code Fast) are edit-format changes, this is the highest-value dimension nobody besides Rombaut codes.

**Convergence (covered by four or five of five):** A3 context compaction, B5 protocol standardization, C1 loop primitives (at differing granularity), D2 long-term memory, G1 execution isolation, F2 cost controls. These are the dimensions where our contribution is scale and evidence, not novelty.

**Where their categories conflict with ours (decide before schema freeze):**
1. *Sandbox placement.* Li = E; Guo = V; Rombaut = Layer 2; Meng = challenge + Security column; ours = G. Keep G but state the mapping explicitly in the paper.
2. *State vs lifecycle.* Li folds state into L and argues against a separate state component (§2.3); Meng and Rombaut separate it. Our D layer follows Meng/Rombaut; expect a reviewer from the Li camp.
3. *Loop primitives: single label vs multi-select.* Li Table 2 assigns one "Primary Pattern" per system; Rombaut finds 11/13 compose primitives and argues single labels "obscure the design decisions" (§5.1). Our C1 is multi-select; Rombaut is our precedent.
4. *Evaluation infrastructure as harness.* Meng and Li include benchmarks/evaluators as systems; we do not. Our inclusion criterion (a) must say "an agent system", and our related-work must say why HAL, OSWorld and BrowserGym are in their N but not ours.
5. *Persistent memory vs static instructions.* Rombaut refuses to count CLAUDE.md-style files as memory because "the agent never writes or updates them" (§4.3.4). Our D2 value `file_notes` conflates the two. Split into `static_instruction_files` (read-only) and `agent_written_notes`.
6. *Missing dimensions on our side.* Rombaut's Loop driver (user / scaffold / LLM; "arguably the most fundamental architectural distinction", §4.1.2), Tool discovery strategy (static / per-phase / config-conditional / per-turn / dynamic-MCP), and Multi-model routing (Rombaut §4.3.3; Banu's Φ; Guo §2.4) have no dimension of ours to map to. One clarification, because section C of this document is more precise than this sentence: only **Loop driver** has no crosswalk row at all, so for that one "no counterpart" is exact. The other two are marked *partial* in section C — B4 `tool_schema_source` covers static against dynamic/MCP registration but not hand-written against generated, and F2 `cost_controls` touches multi-model routing only through budget. **Cite the strict reading in the manuscript:** all three lack a dimension of ours, and two are touched only partly, in exactly those ways. Loop driver and multi-model routing are cheap to add and both authors give us the value sets; Control flow implementation (while / recursion / graph / exception) is too code-level and can be omitted.
7. *V means two things.* Meng's V is trajectory-capture-for-offline-evaluation; Guo's V is in-loop verification plus governance; Li's V is a five-stage evaluation lifecycle. Our E1 (self-verification) and H3 (eval hooks) must map to each separately; the crosswalk table already does.
8. *Prompt in or out.* Rombaut out; others in. Our A1 stays in, with the manual rule that prompt-only systems fail inclusion criterion (a).

## E. Claims in these surveys our data can test

Each is falsifiable with `systems.csv` (+ `results.csv` where noted); "M×B fixed" means benchmark × base-model fixed effects.

1. **Rombaut §4.2.2, §5.2:** edit formats are "trending toward string replacement" (5/13). Test: share of `search_replace` in B3 across N systems, and its trend against M5 first-release date.
2. **Rombaut §5.2:** dimensions converge "where external constraints dominate (tool capability categories, edit formats, execution isolation) and diverge where open design questions remain (context compaction, state management, multi-model routing)". Test: per-dimension normalized entropy of value distributions (RQ2); prediction is entropy(B3, G1) < entropy(A3, D1, F2-routing).
3. **Rombaut §4.1.1, §5.4:** "11 of 13 agents compose multiple primitives rather than relying on a single control structure". Test: distribution of |C1| over the corpus; prediction P(|C1| ≥ 2) ≈ 0.85.
4. **Rombaut §4.2.5, §5.2:** isolation "converges on Docker containers for benchmark agents" while interactive agents diverge. Test: G1 × (M4 primary_artifact = paper vs repo, or benchmark-oriented vs CLI category); Cramér's V.
5. **Rombaut §4.3.4:** benchmark-only agents lack persistent memory; interactive CLI agents implement it. Test: D2 = none × M4/M1.
6. **Rombaut §5.3, §6.2:** loop driver correlates with retrieval paradigm (scaffold-driven systems invest in scaffold-side retrieval). Test: C1 ∋ fixed_pipeline/plan_execute vs A2 ∈ {embedding_rag, retrieval_bm25, file_tree_summary}; better if we add the loop-driver dimension.
7. **Guo §7.3:** "Scaffold complexity does not predict effectiveness" (mini-SWE-agent 76.8% vs OpenHands 77.6% under Opus 4.5). Test: regress score on B2 tool count and on the count of non-`none` mechanisms across A3, C2, C3, D2, E1, E2, F2 with M×B fixed; prediction is a null or negative coefficient.
8. **Guo §7.4:** for fixed model, harness choice shifts Terminal-Bench 2.0 by ≥10 points for 14/20 models (median range 13.6). Test: replicate the within-model spread on our `results` table, then attribute the spread to coded dimensions (the step Guo cannot take).
9. **Guo §7.3:** vendor scaffolds beat the best open-source scaffold by 2–4 points on same-generation Claude and Gemini models. Test: M2 open_source × score, M×B fixed.
10. **Guo §6.2, Table V:** software engineering is "verification-dominant", web/GUI is "grounding-dominant". Test: P(E1 ∋ test_execution | M1 = swe) > P(E1 ∋ test_execution | M1 = web/gui); P(A4 ∋ screenshots or a11y_tree | web/gui) high; P(G4 ≠ none | web/gui) > P(G4 ≠ none | swe).
11. **Li §2.9:** "Observability and governance are thinner in open-source coverage" than execution, tools, lifecycle and verification. Test: not-reported / `none` rates for H1–H4 and G4 vs for B1, C1, G1 (RQ4 heatmap).
12. **Li §4.2 and Meng §6.4.4:** "fewer but better tools" / "over-tooling degraded agent performance". Test: sign of the B2 coefficient on score, M×B fixed; also B2 vs cost per instance where reported.
13. **Li §7.4, §12.5 (Anthropic Opus 4.5 → 4.6 removed context resets, $200 → $125):** "every harness component encodes an assumption about what the model cannot do on its own", so scaffolding should thin as models strengthen. Test: number of active mechanisms vs base-model generation and vs M5 date, within domain.
14. **Li §3.2 synthesis:** "Plain Docker containers occupy a diminishing middle ground" between microVMs and OS-level permission sandboxes. Test: share of G1 = container by release year; prediction is decline after 2025.
15. **Meng abstract, §5.1.2:** "systems mature enough for real-world production deployment consistently exhibit a complete implementation of all six architectural components"; "the four full-stack harnesses cluster distinctly". Test: map our dimensions onto E,T,C,S,L,V (E ← C1/F1/E2; T ← B1–B5; C ← A2/A3; S ← D1–D3; L ← G4/H4; V ← H1/H3), define completeness as count of non-`none`, and check whether it separates production systems (repo/tech-report artifact, high M7) from paper-only systems; also test whether the clustering survives at N ≥ 150.
16. **Meng §3.2.1:** the evaluation interface is "partial or absent in 14 of 22 systems". Test: rate of H3 = none and H1 ∈ {none, logs}.
17. **Meng Table 3, §3.5:** S and L become "Required" for software engineering, long-running assistants and multi-agent systems. Test: P(D3 ≠ none) and P(G4 ≠ none or H4 ≠ none) by M1 and by C3 ≠ single.
18. **Rombaut §4.3.3:** 10/13 route to multiple models and cost is the primary driver. Test: rate of F2 ∋ model_routing (or the new routing dimension) and its association with M4 = repo.
19. **Banu §3.5, §6.2:** harness structure is model-parametric (same harness, different Φ). Test: among systems with results on ≥2 base models (M3 = yes), is the harness's rank order across benchmarks stable? A weak test, but it is the only empirical hook Banu offers.

## F. Our four differentiators, restated against what was found

**1. PRISMA rigor.** Still ours, but the plan's sentence "None of the above is systematic" must be softened. Li §2.5 explicitly invokes "the reporting discipline of systematic reviews" citing Page et al. 2021 (PRISMA 2020), states four source streams, inclusion/exclusion criteria (§2.6), a coding protocol (§2.7) and corpus limitations (§2.8). Meng §5.1.1 gives inclusion criteria, a keyword search over five venues and a time window, though it explicitly disclaims PRISMA. Rombaut publishes a candidate pool with per-exclusion rationale (Appendix A) and a 296-claim verification pass (§6.1). What none of them has: recorded search strings with hit counts per source, a flow diagram, dual independent screening, coded exclusion reasons at full-text stage, pre-registration, or any inter-coder agreement (Li: "we do not report Cohen's kappa"). Restate as: *the first pre-registered, dual-screened, dual-coded review of agent harnesses with per-dimension agreement statistics.* Drop "first systematic".

**2. Dataset scale with evidence per cell.** Holds on the product N × D × evidence, but the plan's "best existing is 23 × 6 or 13 × 12" is wrong on N. Li's catalog is 368 entries with one category, tags, stars, license, and a one-sentence `why_included` rationale, plus Table S1's one-primary-layer coding of 138 artifacts, Table 2's two-variable coding of 18 systems and Table 4's six-variable coding of 10 systems. Meng's matrix is 23 × 6 (+2) with no evidence and no machine-readable release. Rombaut's 13 × 12 is the only prior work with per-cell file:line evidence. Neither survey's HF "dataset" contains data; both contain a PDF. So: nobody has more than ~12 dimensions per system with evidence, and nobody has evidence per cell at N > 13. Restate as: *depth × breadth × evidence*, and cite Rombaut as the evidence standard we adopt at 10× the N. Caveat: Li's N is inflated by counting sandboxes, tracers, gateways and benchmarks as entries; say so rather than compare 150 to 368.

**3. Corpus-wide quantitative synthesis.** Weaker than assumed. Guo §7.3–7.5 already performs observational, corpus-level, same-model/different-harness analysis on three benchmarks using public leaderboard logs (48 matched Terminal-Bench submissions; ~35 SWE-bench rows; WebArena slices) and reports within-model spreads. The plan's Section 0 table lists Guo under "Design→score analysis? No"; that is incorrect. What Guo does not do is code any design feature, so the harness is a nominal label and no design-to-outcome regression is possible. Restate as: *the first synthesis that regresses reported outcomes on coded design dimensions (with benchmark × model fixed effects) rather than on harness identity.* Also: Guo's Tables VII–IX are a ready-made seed for our `results` table and should be cited as such, and HAL, AgencyBench, SkillsBench and MASEval (all cited by Meng) are the controlled-experiment counterparts we must position against.

**4. Crosswalk.** Holds at dimension level; partial crosswalks exist at layer level. Li §2.3 maps ETCLOVG against Meng's tuple (state → L, hooks → G); Banu §2.5 maps E,T,C,S,L,V onto (G, Know, Φ) and says a precise mapping "is developed elsewhere"; Guo Table I tabulates both surveys by lens. Nobody crosswalks Rombaut's 12 dimensions to any of the layer schemes, and nobody reconciles five schemes at once. Restate as: *a dimension-level crosswalk of five prior schemes (ETCLOVG-7, Meng-6, Guo-6, Rombaut-12, Banu's triple)* and fix the plan text, which treats ETCLOVG and H=(E,T,C,S,L,V) as one paper.

**New threats surfaced while reading (not in the plan; not read in full, abstracts only):**
- **Barbaste et al., arXiv:2609.00006 (created 2026-07-15, updated 2026-09-02), "Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents — A Source-Code Study of Eleven Systems."** Source-code anatomy of 11 production coding harnesses (Claude Code, Codex CLI, Gemini CLI, Mistral Vibe, OpenHands, Aider, Mini-SWE-Agent, Hermes, Pi, OpenCode, OpenClaw) plus Omnigent, across "seven canonical subsystems", 13 observations, 29 design patterns, ~4M LOC, and a re-pinned longitudinal sample across one quarter. This is Rombaut's method at similar N with a longitudinal axis and a seventh taxonomy. It must be read in full before the protocol freezes; it likely becomes a sixth column in the crosswalk.
- **Zhong and Zhu, arXiv:2605.13357, "AI Harness Engineering: A Runtime Substrate for Foundation-Model Software Agents."** Eleven component responsibilities and an H0–H3 ladder. Another taxonomy to reconcile.
- **Zhang et al., arXiv:2605.23950, "Stop comparing LLM agents without disclosing the harness"** (cited by Li §8.1, §11.3, §12.5) and **He et al., "Harness engineering for language agents: the harness layer as control, agency, and runtime" (HARNESSCARD; cited by Meng §2.0.4, §7.2)**, whose audit of 40 papers found a majority do not report harness configuration. Both anticipate our RQ4 "not reported" finding and must be cited as prior evidence.

## G. Must cite, and how

- **Guo et al.
